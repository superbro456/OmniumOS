# OmniumX и Omnium OS — архитектура

Единое описание процессора **OmniumX** и операционной системы **Omnium OS (Aurora)**.
Чип и ОС проектируются вместе: то, что ОС делает часто (проверка прав, обмен
сообщениями, переключение задач), чип делает аппаратно и дёшево.

Главные цели всей платформы: **лёгкая, умная, защищённая**.

- **Лёгкая** — маленькое ядро, данные не копируются, а передаются по владению.
- **Умная** — система сама подстраивает ресурсы под нагрузку и замечает аномалии.
- **Защищённая** — права проверяются по ключу до того, как данные тронуты, и это делает железо.

## Часть I. Процессор OmniumX

### 1. Общая концепция

OmniumX — масштабируемая RISC-архитектура, которая объединяет в одном
адресном пространстве:

- вычислительные ядра двух типов (тяжёлые и лёгкие);
- общий **цех умножения** для графики и ИИ;
- аппаратную охрану памяти на каждом блоке;
- аппаратную шину сообщений **Omnium Fabric**.

Ключевой принцип: **данные приносят заранее и только по ключу**. Поэтому ядра не
ждут память и не оставляют следов, по которым можно провести атаку.

Это не процессор с ускорителями рядом, а одна архитектура с разными режимами
исполнения. Обычный код, графика, видео и ИИ работают с одними и теми же данными
без копирования.

### 2. Набор команд (ISA)

- RISC, архитектура load/store: считать можно только в регистрах, в память ходят
  отдельными командами `LOAD` / `STORE`.
- Фиксированная длина команды — 32 бита. Первые 7 бит — код операции, дальше поля
  регистров и непосредственного значения.
- Регистры: 31 целочисленный (`H0`–`H30`) и 16 с плавающей точкой (`F0`–`F15`).
- Флаги `Z` (равно) и `N` (меньше) выставляет `CMP`, условный переход должен идти
  сразу после него.

**Базовый набор** — 60–80 команд, его обязана поддерживать любая конфигурация:

| Группа | Команды |
|---|---|
| Целая арифметика | `SUM SUB MUL DIV MOD FLOORDIV POW INC DEC NEG ABS MIN MAX` |
| Float | `FSUM FSUB FMUL FDIV FPOW FNEG FABS FSQRT ITOF FTOI` |
| Логика и сдвиги | `AND OR XOR NOT SHL SHR SAR BIT_TEST BIT_SET BIT_CLEAR` |
| Память и стек | `LOAD STORE LOADF STOREF PUSH POP MOV LEA` |
| Переходы | `CMP TEST JMP JE JNE JL JLE JG JGE JZ JNZ CALL RET` |
| Атомарные | `ATOMIC_ADD ATOMIC_SWAP ATOMIC_CAS` |
| Система | `SYSCALL SYSRET IRQ_ENABLE IRQ_DISABLE HALT NOP YIELD GET_TIME` |

**Расширения** подключаются по необходимости (общий объём с базой — около 250 команд):

| Расширение | Что добавляет |
|---|---|
| `X-ATOM` | остальные атомарные операции, `WAIT` / `NOTIFY` |
| `X-VEC` | векторные `VADD VSUB VMUL VDIV VLOAD VSTORE` и логика |
| `X-MAT` | команды цеха умножения (режимы 32 / 8 / 4 бита и троичный) |
| `X-SEC` | `CHECK_PERM SECURE_CALL SECURE_RET`, работа с ключами |
| `X-CRYPT` | `AES_ENC AES_DEC SHA256 SHA512 RNG` и подписи |
| `X-DBG` | `TRACE DEBUG PRINT PRINT_STR` (для эмулятора и отладки) |

Деление на базу и расширения держит лёгкие ядра маленькими: им не нужно
поддерживать то, что делает цех умножения или крипто-блок.

### 3. Привилегии, память и прерывания

Это фундамент, на котором стоит защита Omnium OS.

- **Уровни привилегий.** Режим ядра (кольцо 0) и пользовательский режим. Опасные
  команды (`IRQ_DISABLE`, смена таблиц страниц, порты устройств) в пользовательском
  режиме вызывают исключение.
- **MMU.** Страницы по 4 КБ. У каждой программы своя карта памяти, чужие страницы
  ей просто не видны.
- **Ключи доступа.** Каждая страница помечена ключом владельца. Ядро, разведчик или
  устройство сначала сверяет ключ и только потом обращается к данным.
- **IOMMU.** Такой же охранник стоит перед видеокартой, сетью, диском: устройство
  видит только выданные ему буферы.
- **Прерывания.** Таймер, контроллер прерываний и межъядерные сигналы (IPI). Процессор
  сохраняет состояние, вызывает обработчик и возвращается.
- **Системный вызов.** `SYSCALL` переводит программу в ядро по одной заранее
  известной двери, `SYSRET` возвращает её обратно.
- **Быстрое переключение контекста.** Регистры задачи сохраняются аппаратно пачкой,
  потому что Omnium OS часто переключается между службами.

### 4. Ядра: тяжёлые и лёгкие

| Тип | Для чего | Устройство |
|---|---|---|
| Тяжёлое ядро | основная работа программ, игры, компиляция | широкий конвейер, out-of-order, предсказание переходов, три разведчика |
| Лёгкое ядро | фоновые службы, сеть, датчики, службы ОС | короткий конвейер по порядку, низкое потребление, только разведчик-снабженец |

Конвейер тяжёлого ядра: Fetch → Decode → Rename → Schedule → Execute → Commit,
с переименованием регистров и упорядоченной фиксацией результатов.
Лёгкое ядро — классический 5-ступенчатый конвейер Fetch → Decode → Execute →
Memory → Writeback.

### 5. Разведчики

У каждого тяжёлого ядра есть три помощника, которые готовят работу заранее, пока
ядро считает. Аналогия: повар и его помощники, которые раскладывают продукты к
следующему шагу рецепта.

| Разведчик | Что делает | Угадывает? | У каких ядер |
|---|---|---|---|
| Разведчик 1 | готовит самый вероятный путь программы | да | тяжёлые |
| Разведчик 2 | готовит второй путь, только на сомнительных развилках | да | тяжёлые |
| Разведчик 3, «снабженец» | заранее приносит данные, которые точно понадобятся | нет | тяжёлые и лёгкие |

Снабженец ничего не угадывает: он идёт по уже известным адресам (массив, следующий
кадр, следующий блок весов нейросети) и подаёт данные к нужному такту.

**Правила для всех разведчиков:**

1. Сначала проверить ключ (право программы на данные), только потом брать данные.
2. Класть данные на **личный поднос** ядра, а не в общий кэш.
3. Если программа пошла по другой ветке, поднос очищается бесследно. Это защита от
   атак вроде Spectre: по ложному пути ничего не попадает в общие кэши.
4. Запрос без ключа на настоящем пути программы уходит событием в Security Core.
   Запросы на ложных ветках не считаются.

### 6. Кэш и память

- `L1I` / `L1D` — приватные у каждого ядра.
- `L2` — у ядра или кластера.
- `L3` — общий, с учётом NUMA.
- Личные подносы разведчиков — отдельно от кэшей, очищаются при ошибке предсказания.
- Внешняя память: HBM для H-серии, LPDDR5/5X для M-серии.

Кэши обязательны: чем быстрее ядро, тем дороже ему ждать память. Разведчики не
заменяют кэш, а делают так, чтобы нужное оказывалось в нём вовремя.

### 7. Цех умножения: один блок для графики и ИИ

И графика, и нейросети почти целиком состоят из операции `a × b + c`, поэтому у
OmniumX один общий цех с несколькими режимами:

| Режим | Для чего | Как считает |
|---|---|---|
| 32 бита | графика, физика, координаты x, y, z | 1 умножение за раз |
| 8 бит | обычные нейросети | 4 умножения за раз на том же месте |
| 4 бита | сжатые нейросети | 8 умножений за раз |
| троичный (−1, 0, +1) | нейросети в стиле BitNet b1.58 | без умножения: прибавить, вычесть или пропустить |

Четыре приёма экономии энергии и места:

1. **Троичные веса.** В ИИ-режиме умножитель заменяется сумматором. Вес занимает
   около 2 бит вместо 16.
2. **Пропуск нулей.** Вес 0 не считается и даже не читается из памяти.
3. **Рисование плитками.** Кадр рисуется маленькими квадратами во внутренней памяти
   чипа, наружу уходит только готовый квадрат.
4. **Снабженец подаёт ленту.** Числа текут по сетке умножителей (систолический
   массив), каждое читается из памяти один раз и используется много раз.

Тригонометрию (`sin`, `cos`) и корень считает небольшой общий блок спецфункций.

### 8. Блоки SoC

| Блок | Зачем | Связь с Omnium OS |
|---|---|---|
| Ядра с разведчиками | обычные вычисления | Process Core |
| Цех умножения | графика и ИИ | AI Core, GUI в Plant 2 |
| MMU и IOMMU | охранник у каждого блока, в том числе у GPU и сети | Memory Core, изоляция Plants, zero-copy |
| Security Island | отдельное маленькое ядро с ключами и Secure Boot | Core Sanctum, Key Migration |
| Почтовые ящики в Fabric | аппаратный FlexIPC по ключам | FlexIPC, capabilities |
| Sentinel | датчики и счётчики, только чтение | Metrics Core |
| Крипто-блок | AES, SHA, подписи отдельным цехом | Security Core, OFS3 |
| Power islands | выключение ненужных блоков | Passive Watch Mode |
| Аппаратный сторож (watchdog) | перезапуск зависшей службы или переход в EMERGENCY | Central Core |
| Таймер, контроллер прерываний, UART | база для планировщика и отладки | Process Core |

### 9. Omnium Fabric

Внутренняя сеть чипа (mesh или кольцо) с почтовыми ящиками. Сообщение между
службами — это запись в ящик получателя. Fabric проверяет ключ отправителя и сам
будит ядро получателя. Это аппаратная форма FlexIPC.

### 10. Физическая реализация и серии

- 3D-кристалл из двух слоёв, соединённых Hybrid Bonding.
  - **Слой 1 — логика и управление:** ядра, L3, планировщики частоты, ввод-вывод,
    Security Island, питание.
  - **Слой 2 — параллельные вычисления:** цех умножения, векторные массивы, блоки
    трассировки лучей, локальные кэши.
- Целевой техпроцесс — 2 нм.
- **H-серия:** 250–1000+ Вт, HBM, рабочие станции и ИИ.
- **M-серия:** 15–85 Вт, LPDDR, ноутбуки и мобильные устройства.

Это одна архитектура в разных конфигурациях. Направление на будущее для
исследований: многослойные 2D-материалы (графен, h-BN) для межслойного теплоотвода.

## Часть II. Omnium OS

### 11. Устройство: маленькое ядро и кольца служб

Omnium OS — это маленькое быстрое ядро **FlexKernel**, вокруг которого службы стоят
кольцами: чем важнее и опаснее служба, тем ближе к ядру и тем строже её проверяют.
По духу это сочетание идей Fuchsia (службы и ключи-права), seL4 (маленькое
проверяемое ядро), QNX (быстрые сообщения между службами) и confidential
computing (данные программы закрыты даже от соседей).

| Кольцо | Кто там живёт | Если упадёт |
|---|---|---|
| 0 | Central Core: планировщик, память, ключи, FlexIPC | сердце системы, поэтому маленькое и проверенное |
| 1 | Security Core, Memory Core, Process Core | перезапускается по сигналу сторожа |
| 2 | драйверы (диск, сеть, видеокарта) | перезапускается, система живёт дальше |
| 3 | Plants и программы пользователя | падает только сама программа |

### 12. Core-модули ядра

**Central Core** — главный координатор. Запускает остальные модули, раздаёт ключи,
переключает режимы MONO / DISTRIBUTED / EMERGENCY, маршрутизирует системные
события. Его код верифицируется формально, а аппаратный сторож переводит систему в
EMERGENCY, если Central Core перестал отвечать.

**Process Core** — планирование и CPU-время.

- Очередь задач у каждого ядра своя, глобальной очереди нет.
- Строгие приоритеты: активное окно → недавние → полуфон → глубокий фон.
- Бюджеты времени: неиспользованное время (`wants_cpu = false`) уходит в общий запас
  и отдаётся фону.
- Фон гарантированно получает ход: каждый 8-й выбор отдаётся фоновой задаче, если
  она ждёт.
- Тяжёлые задачи идут на тяжёлые ядра, фоновые службы — на лёгкие.

**Memory Core** — политика над физической памятью.

- Три зоны: **Kernel**, **FastApp** (программы), **Service** (службы).
- Размер зон считается от реального объёма памяти и начинается после образа ядра.
- Service выдаёт память сверху вниз, поэтому свободное место у неё всегда снизу, и
  FastApp может забрать его, не задевая живые данные служб.
- Границы зон двигаются в две фазы: сначала Ironveil закрывает доступ к участку,
  затем Memory Core переносит границу.

**Security Core** — мозг безопасности: собирает события, ведёт аудит, принимает
решения, управляет карантином и шестью слоями защиты.

**Metrics Core** — телеметрия. Получает данные только от датчиков Sentinel и не
принимает код от системы.

**AI Core** — анализ поведения и прогноз нагрузки. Работает в одностороннем канале:
видит показатели железа и советует, но сам недоступен для программ. Решения
принимает не он, а политики Security Core и Optimize Core.

**Optimize Core** — баланс между задержкой и пропускной способностью, NUMA,
адаптивная буферизация.

### 13. Режимы работы

- **MONO** — минимум модулей, один активный Plant, минимальная задержка
  (встраиваемые системы, восстановление).
- **DISTRIBUTED** — все модули и Plants активны, параллельная обработка.
- **EMERGENCY** — частичное объединение ядра, минимум изоляции, максимум
  производительности для аварийных сценариев.

### 14. Plants — изолированные домены

| Plant | Назначение |
|---|---|
| Plant 1 | сеть, ввод-вывод, драйверы |
| Plant 2 | приложения пользователя, GUI |
| Plant 3 | системные службы |
| Plant 4 | песочница и карантин |
| Plant 5 | Legacy Bridge — программы других ОС |

У каждого Plant своё адресное пространство, ограниченный набор каналов FlexIPC и
свои политики доступа.

### 15. FlexIPC

Шина сообщений между модулями, Plants и службами.

- **Передача владения вместо копирования.** Данные не копируются: права на
  страницу переходят от отправителя к получателю.
- **Capabilities.** Право на память передаётся защищённым токеном, а не указателем.
  Доступ у отправителя пропадает в тот же миг, когда появляется у получателя.
- **Приоритетные каналы** для служб реального времени.
- **Zero-trust** внутри ОС: каждый канал проверяется по ключу.
- На OmniumX FlexIPC работает через почтовые ящики Fabric; на x86 — через общую
  память, блокировки и межъядерные прерывания.

### 16. Графика: проверка один раз

Графика защищена не проверками на каждом кадре, а одной проверкой ключа при выдаче
буфера. Дальше данные переходят от владельца к владельцу, а охрану держит железо.

Путь одного кадра:

1. **Выдача буфера.** Security Core и Memory Core проверяют права один раз и выдают
   ключ. IOMMU и MMU видеокарты запоминают, кому доступна эта память.
2. **Рисование.** Программа пишет команды в свою очередь, видеокарта рисует в буфер.
   Ядро ОС в этом не участвует.
3. **Передача композитору.** Программа отдаёт владение буфером композитору (службе,
   которая собирает окна).
4. **На экран.** Композитор собирает кадр и передаёт его выводу на экран. Кадр ни
   разу не скопирован.
5. **Возврат.** Буфер возвращается программе для следующего кадра без новой
   проверки.

Принципы: своя очередь команд у каждой программы, драйвер видеокарты — отдельная
служба во втором кольце (его сбой не роняет систему), тонкий явный интерфейс в духе
Vulkan. На x86 используются открытые драйверы Mesa с тонкой прослойкой Omnium,
на OmniumX тот же интерфейс работает с цехом умножения и рисованием плитками.
Программа не знает, на каком чипе она рисует.

### 17. OmniumFS (OFS3)

Платформа хранения с объектной моделью.

- `Programs/` — контейнеризированные приложения;
- `Users/` — данные, проекты, версии;
- `System/` — ядро, драйверы, критические компоненты.

Версии и снапшоты, подписи и проверка целостности, самовосстановление. OFS3
связана с Security Core и Memory Core и является последним рубежом защиты.

### 18. Многоуровневая защита

Безопасность — не отдельный модуль, а сквозная архитектура. Security Core управляет,
шесть слоёв исполняют:

1. **Aethis Layer** — сетевой периметр: фильтрация, защита от DDoS, IDS/IPS.
2. **Phantom Layer** — обман и ловушки: фальшивые процессы, honeypot.
3. **Voltbreaker Layer** — активное вмешательство: перехват системных вызовов,
   обрыв подозрительных операций, перенос в Plant 4.
4. **Ironveil Layer** — защита ядра и памяти: критические адреса, защита от ROP/JOP.
5. **Shadow Bastion** — скрытые пространства: процесс видит только разрешённое.
6. **Core Sanctum** — финальный рубеж: ядро, OFS3, драйверы, криптография.

Опорные механизмы:

- **Белые списки системных вызовов.** Каждый процесс может вызывать только свои
  разрешённые вызовы; остальное — сразу карантин в Plant 4.
- **CARP (Context-Aware Resource Policing).** AI Core сравнивает нагрузку с
  «отпечатком» программы: если калькулятор греет процессор как игра, процесс
  блокируется.
- **Защита от атак по сторонним каналам.** Разведчики проверяют ключ до доступа и
  чистят подносы на ложном пути; Metrics Core читает только датчики Sentinel.

### 19. Ключи и удалённый контроль

- **Key Migration.** При краже мастер-ключ из Security Island переносится в облако,
  локальная копия стирается.
- **Active Beacon.** Служба в Aethis Layer передаёт геолокацию владельцу даже при
  заблокированном интерфейсе.
- **Autonomous Freeze.** Без подтверждения от сервера в течение N часов доступ к
  памяти блокируется.
- **Offline Deadman Switch.** При глушении связи в режиме тревоги устройство само
  уничтожает части мастер-ключа (схема Шамира).

### 20. Энергия: защита по требованию

- **Passive Watch Mode.** В покое тяжёлые слои защиты спят, работают Metrics Core и
  лёгкие модели AI Core; ненужные блоки SoC выключены через power islands.
- **Cascade Activation.** При попытке доступа к чужой памяти или портам мгновенно
  просыпаются Voltbreaker и Ironveil.
- **Аппаратная криптография:** крипто-блок OmniumX, AES-NI на x86, NEON на ARM.

### 21. Legacy Bridge (Plant 5)

Программы других ОС работают через слой трансляции (на базе Wine и бинарных
трансляторов) внутри Plant 5.

- Песочница по умолчанию, нулевое доверие, нет прямого доступа к OFS3.
- Voltbreaker знает только минимальный стерильный набор вызовов; всё остальное
  эмулируется внутри Plant 5.

## Часть III. Как чип и ОС работают вместе

| Что нужно Omnium OS | Что даёт OmniumX |
|---|---|
| строгая изоляция | привилегии, MMU, IOMMU, ключи на страницах |
| много сообщений между службами | почтовые ящики Fabric |
| частые переключения задач | аппаратное сохранение контекста |
| zero-copy | смена владельца страницы одной операцией |
| защита от Spectre | разведчики с проверкой ключа и личными подносами |
| ИИ и графика | цех умножения с троичным режимом |
| Passive Watch Mode | power islands, Sentinel |
| EMERGENCY | аппаратный сторож |
| фоновые службы | лёгкие ядра со снабженцем |

**Скорость.** Классические системы (Windows, macOS) несут решения прошлого
поколения. Новая эпоха — ИИ, безопасность, много ядер — просит новых архитектур.
Omnium выигрывает за счёт того, что чип и ОС придуманы вместе: данные приходят
заранее, права проверяет железо, сообщения идут без копирования. На обычном x86
выигрыш дают маленькое ядро, быстрый FlexIPC и графика с проверкой один раз.

## Часть IV. Состояние реализации

### Ядро Omnium OS для x86 (этот репозиторий)

Работает и проверяется в QEMU (`make test CROSS=`):

- загрузка через GRUB (Multiboot), свой стек загрузки;
- GDT, IDT с обработчиками исключений, контроллер прерываний и таймер 100 Гц;
- запуск второстепенных ядер (AP) со своим стеком у каждого, проверено на 1, 2 и 4 ядрах;
- зоны памяти по реальному объёму RAM (проверено от 64 МБ до 1,5 ГБ);
- планировщик с очередями по приоритетам и гарантированным ходом для фона
  (`make unittest`);
- FlexIPC-очередь с блокировкой, Security Core с белым списком вызовов и карантином;
- вывод на экран с прокруткой и копией в последовательный порт.

Следующие шаги: переключение контекста и первые задачи, пользовательский режим и
системные вызовы, страничная память, список ядер из таблицы ACPI MADT, драйверы
клавиатуры и диска.

### Эмулятор OmniumCPU и язык Flang (`emulator/`)

- Эмулятор на Python: регистры `H` и `F`, флаги, стек, вызовы функций, атомарные
  операции, несколько ядер по очереди.
- Компилятор Flang: переменные, `int` / `float`, `if`, `while`, `for`, функции с
  рекурсией, вызов до объявления.
- Тесты: `python3 -m pytest tests` в папке `emulator`.

Следующие шаги: кодирование команд в 32 бита, привилегии, прерывания и MMU в
эмуляторе, затем запуск на нём маленького ядра Omnium OS и замеры идей OmniumX
(разведчики, ключи, троичный цех).
